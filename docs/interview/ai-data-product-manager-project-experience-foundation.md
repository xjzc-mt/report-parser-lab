## 0. 项目边界先说清楚

### 0.1 简历主项目是什么

简历主项目应该讲：

> 面向 ESG / 可持续发展报告的多模态报告信息提取系统。

它的核心任务是把企业发布的 PDF 报告，结合一套指标需求表，自动抽取结构化 ESG 指标数据，并输出到 Excel / Hive 表 / 接口表等下游可消费形态。

这个项目不是一个简单 PDF 工具，也不是单纯 Prompt Demo，而是一条从“报告文件 + 指标口径”到“结构化数据资产”的生产链路。

### 0.2 LLM Lab 在项目中的位置

LLM Lab 不是主项目本身，也不应该被说成主项目的 Harness 主体。

更准确的定位是：

> LLM Lab 是围绕主项目结果做研发调试、Prompt 快速迭代、模型结果验收、Prompt 自动优化、成本估算和输入预处理的外部工具平台。

它服务于主项目的质量闭环，尤其是：

- 看模型抽取结果是否正确；
- 看 Prompt 在不同 PDF 上是否稳定；
- 看失败样本集中在哪里；
- 看是否有幻觉、漏提、页码错误、单位错误；
- 看输入 PDF、Prompt、模型配置如何影响成本和效果。

### 0.3 原项目自身的 Harness 是什么

主项目自身的 Harness，不是 LLM Lab，而是批量 LLM 抽取运行框架：

- 任务输入封装；
- PDF 下载、压缩、标记、切分；
- Stage1 章节定位；
- Stage2 指标抽取；
- JSONL 请求和响应；
- manifest / summary / 原始响应留存；
- 并发、限流、重试；
- Excel / Hive 原始表 / 接口表输出；
- 可复跑、可排查的中间产物。

面试里如果被问 Harness，应该优先讲这个运行框架，再补充 LLM Lab 是外部验收与 Prompt 迭代工具。

## 2. 我面对的业务问题

### 2.1 业务背景

ESG / 可持续发展报告通常是企业主动披露的 PDF 文档，里面包含环境、社会、治理、财务投入、能源消耗、碳排放、安全生产、员工、供应链等大量指标。

这些数据对数据产品有价值，但原始形态高度非结构化：

- PDF 页数多；
- 版式不统一；
- 有大量表格、图片、扫描页；
- 指标表述口径不一致；
- 同一指标可能跨年份、跨单位、跨章节；
- 部分值只在图片、图例、表格注释中出现；
- 同一公司不同年份报告结构也不同。

传统人工方式通常是：

1. 打开 PDF；
2. 搜索指标关键词；
3. 手动阅读相关章节；
4. 复制值、单位、页码；
5. 填入 Excel 或数据表；
6. 人工复核。

这套方式的问题是：

- 规模上不去；
- 人工成本高；
- 主观误差大；
- 口径难统一；
- 无法快速复跑；
- Prompt 或模型改动后无法系统评估收益；
- 难以沉淀可复用的数据生产链路。

### 2.2 数据产品目标

我把问题定义为一个 AI 数据产品问题，而不是单点模型调用问题。

产品目标包括：

1. **把非结构化 PDF 转成结构化指标数据**
   - 输出不只是自然语言答案，而是稳定字段。
   - 例如：指标编码、指标名称、年份、文本值、数值、单位、币种、分子单位、分母单位、证据页码等。

2. **支持批量报告处理**
   - 从单份 PDF 验证，走向多份 PDF、万份级报告任务。
   - 从本地上传，走向 SQL 输入、对象存储下载、批量任务执行。

3. **支持 500+ 指标的统一口径管理**
   - 指标口径不能散落在 Prompt 里。
   - 需要用需求表维护指标编码、名称、类型、定义、指导语和用户 Prompt。

4. **结果必须可追溯**
   - 每个结果要知道来自哪份报告、哪一页、哪个指标、哪个模型、哪个 Prompt。
   - 不能只输出一个不可解释的结论。

5. **抽取过程必须可复跑**
   - 模型升级、Prompt 调整、指标口径变更后，需要重新跑同一批报告。
   - 需要保留中间产物和原始响应，方便排查。

6. **需要验收闭环**
   - 不能只看模型能不能回答。
   - 要能对比测试集，识别严格通过、宽松通过、单条错误、漏提、幻觉、单位错误、页码错误等。

## 3. 我承担的 AI 数据产品经理职责

这个项目里，我的角色不是单纯写代码，也不是只写 Prompt，而是站在 AI 数据产品经理视角完成从业务定义到数据生产闭环的设计。

### 3.1 需求定义

我做了：

- 把“从 ESG 报告里找信息”拆成明确的数据生产任务；
- 明确输入是什么：PDF 报告、指标需求表、报告清单、模型配置；
- 明确输出是什么：结构化指标结果、证据页码、原始响应、落表结果；
- 明确用户是谁：数据运营、研究员、质检人员、AI 工程人员、数据产品下游使用方；
- 明确验收标准：值是否正确、单位是否正确、页码是否命中、是否漏提、是否幻觉。

### 3.2 指标体系产品化

我把指标从“散落在文档里的需求”产品化为需求表字段：

- `group`
- `chapter_description`
- `indicator_code`
- `indicator_name`
- `value_type`
- `definition`
- `guidance`
- `prompt`

这么做的价值是：

- 指标可以批量维护；
- Prompt 可以按指标维护；
- 指标可以按章节或业务主题分组；
- 结果可以和测试集、接口表稳定关联；
- 后续可以支持 Prompt 资产库和版本管理。

### 3.3 抽取流程设计

我没有把它设计成“一次上传 PDF，一次问模型”的简单流程，而是拆成生产流水线：

1. 读取报告清单；
2. 下载 / 上传 PDF；
3. PDF 压缩与预处理；
4. 按指标需求构建任务；
5. 按指标 group 做章节定位；
6. 根据定位结果切章节 PDF；
7. 按指标类型和批次调用模型；
8. 解析模型 JSON；
9. 做字段映射和结果标准化；
10. 输出 Excel / 原始表 / 接口表；
11. 用测试集或 LLM Lab 做结果验收；
12. 根据失败样本优化 Prompt 和流程。

### 3.4 模型选型与技术路线判断

我参与了多模态模型路线的产品判断：

- ESG 报告不是纯文本；
- 大量信息出现在表格、图片、扫描页、颜色图例、版式结构中；
- 如果只用 OCR + RAG + 文本模型，会丢失一部分视觉信息和结构关系；
- 所以当前主链路采用 Gemini / Vertex 多模态 PDF 输入；
- 但长期最佳实践不是“全部都用最贵的多模态模型”，而是混合路线：
  - 简单文本型指标走 OCR / 文本模型 / RAG；
  - 复杂图表、扫描页、跨页表格、低置信度样本走多模态模型；
  - 通过模型路由在成本和效果之间平衡。

这说明我不是为了用 LLM 而用 LLM，而是在评估输入形态、错误类型、成本结构后做路线选择。

### 3.5 质量验收与迭代机制设计

我把项目从“跑一次结果”推进到“可验收、可复盘、可优化”：

- 设计测试集与 LLM 结果的关联方式；
- 支持手动配置关联字段；
- 支持不同报告标识字段，如 `report_name`、`source_announce_id`、`announcement_id`；
- 处理幻觉行、漏提行、匹配不全行；
- 引入相似度、严格通过、宽松通过、单条错误等分类；
- 建立数值、单位、文本相似度的比较逻辑；
- 通过 `synonyms.xlsx` 和 `conversion.xlsx` 支持同义词与单位换算；
- 用 LLM Lab 支持 Prompt 快速迭代和自动优化。

### 3.6 工程协同与产品化落地

我推动功能从脚本能力走向产品化工具：

- 本地 Vite + React 工作台；
- Prompt 快速迭代页面；
- 模型结果验收页面；
- Prompt 自动优化页面；
- 数据预处理工作台；
- 模型预设管理；
- Prompt 资产库；
- Token 统计；
- PDF 压缩；
- 多输入文件支持。

这些能力让非工程人员也可以参与调试、验收和质量分析。

## 4. 主项目：报告信息提取系统，我具体做了什么

### 4.1 从业务需求抽象出结构化抽取任务

我首先把 ESG 报告抽取定义为“结构化抽取任务”，而不是“问答任务”。

问答任务只需要回答一句话，例如：

> 这家公司 2024 年耗电量是多少？

但结构化抽取任务需要输出稳定字段：

- 报告 ID；
- 报告名称；
- 指标编码；
- 指标名称；
- 指标类型；
- 年份；
- 文本值；
- 数值；
- 单位；
- 币种；
- 强度指标的分子 / 分母单位；
- 证据页码；
- 是否披露；
- 原始响应。

这一步非常关键，因为它决定了后续：

- Prompt 怎么写；
- 模型输出怎么约束；
- 结果怎么入库；
- 测试集怎么设计；
- 如何验收。

### 4.2 设计指标需求表作为产品配置中心

我把“指标要抽什么”沉淀到 Excel / Google Sheet 需求表中。

需求表承担了产品配置中心的角色：

- 维护指标列表；
- 维护指标定义；
- 维护指标指导语；
- 维护用户 Prompt；
- 维护指标分组；
- 维护章节定位描述；
- 维护值类型。

这比把所有内容写死在代码里更适合数据产品：

- 业务人员能维护；
- 版本容易管理；
- 指标口径变化不一定要改代码；
- 同一抽取引擎可以复用到不同指标体系。

### 4.3 设计 `value_type` 抽取策略

ESG 指标不是一种输出形态。我把指标按类型拆分：

#### 文字型

用于抽取政策、举措、技术、管理制度、事件描述。

产品关注点：

- 是否真的满足定义；
- 是否只是相关描述；
- 是否需要保留原文；
- 是否出现“未披露”。

#### 数值型

用于抽取排放量、能耗、水耗、人数、次数等。

产品关注点：

- 千分位；
- 中文数字；
- 单位；
- 年份；
- 小数；
- 百分比；
- 报告中的合并口径。

#### 货币型

用于抽取投入金额、捐赠金额、研发费用等。

产品关注点：

- 币种；
- 万元 / 百万元 / 元；
- 是否需要换算；
- 是否和数值型统一处理。

#### 强度型

用于单位产值碳排、单位营收能耗等强度指标。

产品关注点：

- 分子单位；
- 分母单位；
- 是否为比率；
- 是否需要同时保留 numerator / denominator。

拆分 value_type 的价值：

- Prompt schema 更清晰；
- 模型输出字段更稳定；
- 后续验收指标可以按类型定制；
- 单位、数值、文本相似度可以分开计算。

### 4.4 设计 PDF 多模态输入路线

我判断 ESG 报告适合多模态 PDF 输入，原因包括：

- 报告中有大量表格；
- 指标值经常在表格单元格中；
- 有扫描页，纯文本抽取可能失败；
- 有图例颜色、流程图、图片标注；
- 页码、脚注、表头、跨页表格都依赖版式；
- PDF 的阅读顺序不一定等于文本抽取顺序。

所以主链路不是先把 PDF 全量转成纯文本再问模型，而是让 Gemini / Vertex 直接读取 PDF。

但我也明确了这个路线的边界：

- 多模态更贵；
- 大规模任务不能无脑全文直读；
- 需要章节定位、PDF 切片和批处理；
- 后续应该引入 OCR / RAG / 文本模型作为低成本路线。

### 4.5 设计 Stage1 章节定位

如果把整份报告和所有指标一次性输入模型，会有几个问题：

- 上下文太长；
- 成本高；
- 模型注意力分散；
- 容易从错误章节找答案；
- 页码错误难排查；
- 失败后不能局部重跑。

所以我设计 / 推动了先定位章节的思路：

1. 指标按 `group` 和 `chapter_description` 分组；
2. 先让模型判断某一类指标最可能出现在哪些页；
3. 生成 Stage1 章节定位 JSONL；
4. 得到每个 group 对应的页码范围；
5. 再切出相应章节 PDF。

产品价值：

- 降低单次输入规模；
- 提升答案相关性；
- 减少模型在无关章节中幻觉；
- 中间结果可检查；
- 页码定位可复用。

### 4.6 设计 Stage2 指标抽取

Stage2 基于章节 PDF 和指标 Prompt 做正式抽取。

我关注的不是“模型能不能回答”，而是：

- 是否按 JSON 输出；
- 是否包含所有必须字段；
- 是否能处理多年度结果；
- 是否能区分未披露；
- 是否保留证据页码；
- 是否能按 value_type 输出不同结构；
- 是否能在失败后重试；
- 是否能保留原始响应供排查。

这种设计使模型结果能进入数据生产链路，而不是停留在 Demo。

### 4.7 设计 PDF 准备与文件治理

报告 PDF 不是直接拿来就能稳定处理。

项目里做了：

- PDF 压缩；
- lossless optimization；
- 保守压缩；
- 栅格化；
- 元数据读取；
- 页数统计；
- 图片数量统计；
- locator PDF 生成；
- chapter PDF 生成；
- 文件 manifest 记录。

从产品角度，我关注的是：

- 文件太大导致模型输入失败；
- PDF 损坏导致任务中断；
- 压缩不能损害图表识别；
- 页码必须和模型返回结果对齐；
- 每个中间文件都要能追踪回原报告。

### 4.8 设计页码治理

页码是 ESG 抽取非常重要的证据字段。

但页码不是天然可靠的：

- PDF 物理页码；
- 阅读器页码；
- 报告印刷页码；
- 模型识别页码；
- 切片后的局部页码；
- 原报告全局页码；

这些可能都不一致。

因此项目中通过 locator PDF 和 `PHYSICAL_PAGE` 标记来增强页码对齐。

产品价值：

- 结果可以追溯；
- 质检人员能打开报告核对；
- 下游用户对数据更信任；
- 自动验收可以计算页码命中率。

### 4.9 设计结果标准化与落表

模型输出 JSON 后不能直接入库，需要标准化。

我推动 / 设计了以下逻辑：

- 字段别名兼容；
- 多年度拆行；
- value_type 标准化；
- 未披露归一；
- 文本值和数值分开；
- 单位和币种拆分；
- 强度指标分子 / 分母单位拆分；
- 原始响应留存；
- Excel 输出；
- 原始结果表写入；
- 接口表写入。

这一步体现的是数据产品思维：

> 模型结果不是终点，能被数据产品稳定消费才是终点。

### 4.10 设计批量任务能力

项目从本地单文件工具演进为批量生产能力。

具体包括：

- 从 Hive SQL 读取报告清单；
- 从对象存储下载 PDF；
- 多 PDF 并发；
- 单 PDF 内部分批并发；
- 全局模型并发控制；
- Vertex Batch 异步执行；
- GCS JSONL 输入输出；
- Job 轮询；
- Stage1 / Stage2 分阶段运行；
- 失败重跑；
- 输出 manifest 和 summary。

产品价值：

- 从人工单次处理走向批量生产；
- 支持大规模报告处理；
- 抽取过程有阶段、有状态、有产物；
- 大任务可拆分、可恢复、可审计。

## 5. LLM Lab：我围绕主项目补齐了哪些验收和研发工具

LLM Lab 是第二个目录下的项目，定位是：

> 大语言模型工程实验室，用于沉淀 LLM 工程化落地中的文件解析、Prompt 迭代、模型结果验收、Prompt 自动优化、线上验证和数据预处理能力。

它不是简历主项目，但可以作为“我如何把主项目做成闭环”的关键支撑工具。

### 5.1 平台结构重构

我把原来偏 ESG 单点工具的页面，升级为更通用的 LLM 工程实验平台：

- 测试集工作台；
- 线上验证工作台；
- 数据预处理工作台；
- 说明文档；
- 全局模型设置；
- Prompt 资产库。

这体现了从垂直工具到平台化工具的产品思路。

### 5.2 测试集工作台设计

测试集工作台包含三个子页面：

### 5.3 Prompt 快速迭代

这个页面解决的问题是：

> 一个指标 Prompt 写完后，如何快速在多份文件上试跑，看不同报告下表现是否稳定？

我设计 / 推动了：

- 上传多份 PDF；
- 后续扩展 Excel、CSV、文本、docx 等输入；
- 输入统一的提取目标名称；
- 系统提示词和用户提示词分开；
- 支持指定页码范围；
- 多文件可以分别设置页码；
- PDF 文件保留，不因切换指标反复上传；
- 展示原始模型回复；
- 自动解析合法 JSON；
- 结果汇总；
- 历史记录保留；
- 历史记录删除 / 清空；
- 写入 Prompt 资产库；
- 新增 Prompt 和新版本管理；
- Token 估算；
- 进度信息。

产品价值：

- Prompt 修改后可以快速验证；
- 不需要每次跑完整生产链路；
- 可以横向比较同一 Prompt 在多份报告中的表现；
- Prompt 资产可以沉淀，而不是散落在聊天记录里。

### 5.4 模型结果验收

这个页面解决的问题是：

> LLM 结果和测试集怎么对齐？怎么判断对错？怎么定位失败原因？

我设计 / 推动了：

- 上传 LLM 结果文件；
- 上传测试集文件；
- 手动配置关联字段；
- 支持从上传文件实际列名中选择字段；
- 关联字段持久化；
- 清空后使用默认配置；
- 关联字段严格校验；
- 支持多个关联字段；
- 支持删除关联字段；
- 分析时验证字段缺失和配置错误；
- 计算严格通过、宽松通过、单条错误、漏提、幻觉等分类；
- 支持报告维度、指标维度、类型维度分析；

产品价值：

### 5.5 Prompt 自动优化

这个页面解决的问题是：

- 支持上传 PDF；
- 支持选择单个或多个 indicator；

- 支持从模型结果验收跳转并带入选择范围；
- 支持训练样本和验证样本拆分；
- 支持最大优化轮次；
- 支持目标相似度阈值；

## 7. 我在“模型产品”层面做的关键判断

### 7.1 为什么选择 Gemini / Vertex 多模态

不是因为多模态新，而是因为输入决定了模型能力需求。

ESG 报告里存在：

- 扫描页；
- 图片；
- 表格；
- 跨页表格；
- 图例；
- 颜色标识；
- 非线性排版；
- PDF 阅读顺序错乱；
- 字体和脚注干扰。

如果只用文本 OCR：

- 表格结构可能丢；
- 图例颜色可能丢；
- 图片中的关键信息可能丢；
- 页码和内容对应关系可能乱；
- 多栏文本顺序可能错；
- 单位和表头关系可能错。

因此多模态 PDF 输入是当前主链路的合理选择。

### 7.2 为什么不是“只用多模态”

我也意识到多模态贵，所以最佳实践不是一刀切。

更成熟的路线是：

- 简单文本任务：OCR / 文本模型 / RAG；
- 表格密集任务：表格解析 + 多模态复核；
- 扫描页和图示任务：多模态；
- 低置信度任务：强模型复核；
- 高置信度简单指标：低成本模型先跑；
- 复杂指标：Gemini Pro / Vertex Batch。

这可以在简历或面试中表述为：

> 当前阶段选择多模态作为主链路，是为了先解决复杂 PDF 的召回和质量问题；下一阶段会做模型路由，把低成本 OCR/RAG 与高质量多模态结合起来。

### 7.3 为什么做章节定位

章节定位不是技术炫技，而是产品和成本上的必要设计：

- 降低输入 token；
- 降低无关上下文干扰；
- 增强证据页码；
- 提高可解释性；
- 支持失败局部重跑；
- 支持指标 group 级别优化；
- 方便后续对比不同章节策略。

### 7.4 为什么需要 Prompt 资产库

Prompt 在这种项目里不是临时文案，而是生产规则的一部分。

如果没有资产库，会出现：

- 不知道哪个 Prompt 跑出了哪个结果；
- 不知道谁改了 Prompt；
- 不能回退；
- 测试集结果无法复现；
- 优化结果无法沉淀；
- 多指标 Prompt 维护混乱。

因此我把 Prompt 当成资产管理。

## 8. 我在“质量和验收”层面做的关键设计

### 8.1 从人工验收到自动关联

LLM 结果和测试集之间不是天然一一对应。

我设计了手动关联字段配置：

- 可以关联 `report_name`；
- 可以关联 `source_announce_id`；
- 可以关联 `announcement_id`；
- 可以关联 `indicator_code`；
- 可以关联多个字段；
- 字段来自上传文件实际列名；
- 配置持久化；
- 清空后回到默认配置。

这解决了不同数据源字段名不统一的问题。

### 8.2 幻觉、漏提、错误的处理

我区分了：

- 测试集有，LLM 没有：漏提；
- LLM 有，测试集没有：幻觉；
- 两边都有但值不一致：错误；
- 值一致但格式不同：应通过；
- 单位同义或可换算：应通过或宽松通过；
- 文本语义接近：宽松通过。

这比简单 inner join 更符合 LLM 验收实际。

### 8.3 数值和单位判断

我处理过典型问题：

- `4,056,273` 和 `4056273` 应该相等；
- 中文单位和英文单位要通过同义词或换算表处理；
- `吉焦` 和 `GJ` 这种应进入 synonyms 或 conversion；
- 货币型可以算在 NUMERIC；
- value_type 统一为 `TEXT`、`NUMERIC`、`INTENSITY` 这种标准类型。

产品价值：

- 减少格式差异导致的假错误；
- 让验收更接近业务判断；
- 为后续自动优化提供更可靠的失败样本。

### 8.4 从验收到自动优化

我设计了从“模型结果验收”跳转到“Prompt 自动优化”的链路：

1. 在验收页面看错误；
2. 按相似度区间筛选低分指标；
3. 弹窗选择要优化的指标；
4. 带着关联对比文件进入自动优化；
5. 自动优化读取失败样本；
6. 结合 PDF 切片和基线 Prompt 生成优化建议；
7. 结果进入 Prompt 资产库或快速迭代复验。

这形成了闭环：

> 结果验收 → 错误定位 → 指标筛选 → Prompt 优化 → 复验。

## 13. 面试中不要讲错的边界

### 13.1 不要把 LLM Lab 说成主项目

正确说法：

> 主项目是报告信息提取生产链路，LLM Lab 是外部验收和研发工具。

### 13.2 不要把 LLM Lab 说成原项目 Harness

正确说法：

> 原项目 Harness 是批量抽取运行框架，包括任务封装、Stage1 / Stage2、JSONL、manifest、重试、并发、落表等。LLM Lab 是后置验收和 Prompt 迭代工具。

### 13.3 不要说所有能力一开始就都在

正确说法：

> 项目经历了本地原型、Fast 并发版、Vertex Batch 版、LLM Lab 验收工具几个阶段。

### 13.4 不要说只靠多模态解决全部问题

正确说法：

> 多模态是当前主链路，因为 ESG PDF 复杂；但后续最佳实践是多模态 + OCR/RAG + 模型路由的混合方案。

### 13.5 不要说“直接把整份报告和所有指标丢给模型”

正确说法：

> 通过指标分组、章节定位、章节 PDF 切片、分批抽取来降低噪声和成本。

### 13.6 不要说“模型结果人工看一下就验收”

正确说法：

> 已经设计了测试集关联、相似度、严格 / 宽松通过、漏提、幻觉、单位换算和导出对比文件等验收机制；后续还要进一步沉淀为自动化 evaluation harness。
