报告信息提取项目深度说明

这份文档聚焦你简历中的主项目：报告信息提取 / ESG 指标自动抽取生产链路。 LLM Lab 只是后续研发、调试与验收工具；面试主线应讲这个项目如何把“万份非结构化 ESG/PDF 报告” 转成可落库、可追溯、可复核的结构化指标数据。

万份级年度报告 / ESG 报告批量处理
500+ 指标文字、数值、货币、强度型混合抽取
两阶段章节定位 → 章节切片 → 指标抽取
多模态直接理解 PDF、表格、图示和扫描页
定位 业务问题 版本演进 架构 关键模块 项目内 Harness 路线校准 已实现 未做但必要 面试话术

01项目定位：不是一个“PDF 小工具”，而是 ESG 指标生产流水线

推荐一句话：我做的是一个面向 ESG/可持续发展报告的多模态结构化信息提取系统， 输入是企业 PDF 报告和指标口径表，输出是带指标编码、年份、数值/文本、单位、证据页码和原始响应的结构化结果， 并支持批量任务、章节定位、成本估算、失败重试和后续验收。

目标用户

  • ESG 数据生产 / 数据运营团队
  • 指标体系维护人员、研究员
  • 质检、验收、模型评估人员
  • 后续消费数据的产品、风控、投资研究场景

核心价值

  • 把人工阅读报告改成“自动抽取 + 异常复核”
  • 把不可追溯的答案变成带页码证据的结构化数据
  • 把单次 Prompt 调试变成可批量验证、可复跑的流程

不要混淆

  • report-parser-product：简历主项目，负责生产抽取。
  • ~/AiProjects/llm-lab：LLM Lab，是项目外部的验收、调试和 Prompt 迭代工具，不是主项目本身。

02业务问题：ESG 报告抽取为什么难

输入难

  • PDF 版式差异大：双栏、跨页表格、图片、脚注、附录、扫描页混在一起。
  • 同一指标在不同公司报告里的写法不一致，指标名、章节名、单位都可能变化。
  • 很多关键信息在表格、图例、颜色图块、图片说明里，不是纯正文。
  • 页码存在物理页码、PDF 页码、印刷页码不一致的问题。

输出难

  • 结果不是一句摘要，而是多字段结构：code、name、year、value、unit、currency、page 等。
  • 同一个指标可能跨年度、多值、多单位，需要拆成多行。
  • “未披露”“不适用”“描述型结果”要和真实空值区分。
  • 生产落表要求字段稳定、可追溯、可验收，不允许只给自然语言解释。
指标类型 典型输出 难点
文字型 政策、技术、管理措施、事件描述 需要理解语义边界，避免把相关但不满足定义的内容误提取。
数值型 排放量、消耗量、员工人数、事故数量 要处理千分位、中文单位、量纲、年份、合并口径。
货币型 环保投入、研发投入、公益捐赠金额 币种、单位、百万/万元换算容易出错。
强度型 单位营收碳排、单位产量耗水 分子/分母单位、计算口径和披露原文都要保留。

03版本演进：从本地原型到批量生产

阶段 A：浏览器端原型 / 工作台

仓库根目录的 README 对应最早的 Vite + React 本地工具：上传 PDF 和 Excel/CSV 需求表，调用 Gemini，顺序抽取并导出 Excel，同时提供浏览器端 PDF 压缩。

Vite + React Gemini API Excel 导出 PDF 压缩

阶段 B：CLI / 单批次抽取器

esg-ind-parser/ 下沉为脚本化能力：输入 PDF 和指标需求文件，完成 PDF 准备、指标抽取和 CSV/Excel 结果输出，适合从 UI 原型向自动化迁移。

阶段 C：Fast 生产版

esg_ind_parser_fast 引入 Hive SQL 输入、OSS PDF 下载、异步并发、全局 Gemini semaphore、JDBC 批量写入、原始结果表和接口表双写。

多 PDF 并发 单 PDF 内部批次并发 限流与重试 结果双写

阶段 D：Vertex Batch 两阶段版

esg_ind_parser_batch_inference 把大规模任务改成 GCS + Vertex Gemini Batch：先做章节定位，再切章节 PDF 做指标抽取，降低单次上下文压力，提升大规模吞吐和成本可控性。

Stage1 章节定位 Stage2 指标抽取 JSONL 输入输出 GCS Batch Job

04生产架构：面试时可以这样画

1. 任务输入Hive SQL / 报告清单 / 指标需求表，包含公告 ID、标题、OSS Key、指标定义、Prompt。
2. 文件准备下载 OSS PDF，做压缩、页码标记、元数据读取、必要时栅格化。
3. 章节定位Stage1 用 locator PDF 判断每个指标组所在页码范围。
4. 指标抽取Stage2 基于章节 PDF 与指标 Prompt 调用多模态模型输出 JSON。
5. 标准化落地字段映射、年份拆行、单位处理、原始表 / 接口表双写、Excel 归档。
关键讲法：不是把 500+ 指标和整份 PDF 一次性塞给模型，而是通过指标分组、章节定位、章节 PDF 切片和批量任务，把一个大问题拆成可控的小任务。

05关键模块拆解

指标需求读取与分组

需求表优先读取 用户Prompt sheet，核心字段包括 group、chapter_description、indicator_code、indicator_name、value_type、definition、guidance、prompt。

  • group 用于把同类指标合并到章节定位任务。
  • 无 group 的指标走全文组，避免漏处理。
  • value_type 会规范化，比如文本型可映射为文字型。

Prompt 与结构化输出

系统提示词按指标类型生成不同 JSON schema，模型输出后再做字段兼容映射。

  • indicator_code 可兼容 code/id 等模型别名。
  • text_value、num_value、pdf_numbers 等字段会统一收口。
  • 多年度结果拆多行，便于落表和验收。

PDF 准备与页码治理

生产版包含 lossless optimization、保守压缩、栅格化、插入页码 marker、metadata、page_count、image_count、章节 PDF 生成等能力。

  • 目标是既控制文件大小，又尽量保留图表和扫描页信息。
  • locator PDF 顶部带 PHYSICAL_PAGE: N，用于解决页码对齐问题。

并发、重试与成本

Fast 版用异步并发和全局 semaphore 控制模型调用；Batch 版使用 Vertex Batch 的异步队列方式，把大规模非实时任务从在线调用中拆出来。

  • PDF 操作有超时控制，避免坏文件拖垮全任务。
  • 模型调用有重试和原始结果保留，方便失败排查。
  • Batch 版本包含成本估算入口，适合大规模任务前做预算。

06项目内 Harness：让大规模 LLM 抽取可运行、可复跑、可排查

这里的 Harness 不应该指 LLM Lab。原项目本身的 Harness，更准确地说是围绕“批量 LLM 抽取任务”搭建的一套运行框架： 它负责把输入数据、PDF 文件、Prompt、模型调用、阶段产物、失败重试、成本估算和落表结果组织起来，让万份报告任务不是一次性的脚本调用，而是可追踪、可复跑、可排查的流水线。

Harness 能力 项目中的体现 面试可以强调的价值
任务输入封装 从 Hive SQL / source.sql 读取报告清单，结合需求表生成结构化任务上下文。 把“跑哪些报告、抽哪些指标、用什么口径”从手工参数变成可复用任务定义。
阶段化运行 Stage1 章节定位 JSONL、Stage2 指标抽取 JSONL、locator_pdfs、chapter_pdfs、manifest、summary。 把一个超大 LLM 任务拆成可观察的多个阶段，任何阶段失败都能定位和复用中间产物。
并发与限流 Fast 版有多 PDF 并行、单 PDF 内部批次并发、全局 Gemini semaphore；Batch 版改为 Vertex 异步作业。 避免单机串行太慢，也避免模型 API 被打爆；吞吐和稳定性都有工程控制点。
失败恢复与审计 保留原始请求、原始响应、输出 JSONL、Excel 归档、双写原始结果表和接口表。 不仅能得到最终答案，还能回看模型当时看了什么、答了什么、为什么失败。
质量验收接口 主项目输出标准化结果；LLM Lab 可作为外部验收工具导入结果和测试集做对比。 LLM Lab 是验收环节的工具，不是项目内 Harness 本体；它补上“结果好不好”的可视化评测。
面试表述：原项目的 Harness 是批量抽取流水线自身：任务封装、阶段产物、并发限流、重试、manifest、summary、原始响应留存和落表。 LLM Lab 只作为后置验收/Prompt 调试工具接入，不要把它说成主项目的 Harness。

07重点标记：面试项目路线中容易讲偏的地方

不要把主项目讲成“LLM Lab 提效工具”。 简历项目主线是“报告信息提取生产链路”：PDF 准备、章节定位、指标抽取、结构化落表、批量调度和结果追踪。 LLM Lab 是后续用于验收、Prompt 迭代和对比分析的辅助工具，只能作为质量闭环的一环。
不要把模型路线讲成“只有多模态，不需要 RAG/OCR”。 更合理的说法是：当前主链路采用 Gemini/Vertex 多模态，因为 ESG 报告存在表格、图片、扫描页、颜色图例、复杂版式等纯文本链路难覆盖的内容； 但长期最佳实践应是混合路由：简单文本型任务可走 OCR/RAG/文本模型，复杂版面和低置信度样本再走强多模态模型。
不要说“把整份报告和 500+ 指标一次性喂给模型”。 当前更正确的流程是指标分组、章节定位、章节 PDF 切片、再分批抽取。这样能降低上下文噪声、控制成本、减少跨章节误匹配，也方便失败重跑。
不要把“页码”讲成天然可靠。 PDF 物理页码、印刷页码和模型返回页码可能不一致，所以项目里做了 locator PDF、PHYSICAL_PAGE 标记和章节切片。 面试时应强调页码治理是工程难点，而不是模型随便返回一个页码就能落库。
不要把评测讲成“看几个样例觉得不错”。 原项目本身有原始结果、接口表、Excel 归档和可复跑产物；但严格意义上的自动化 evaluation harness 还不够完整。 更稳妥的表述是：项目已经具备结果留存和后置验收基础，后续需要把测试集指标、失败分类、幻觉率、单位错误率等正式纳入流水线。
不要把原型、Fast 版、Batch 版混成同一个实现。 本地 React 工具是原型/调试入口；Fast 版解决并发和落表；Vertex Batch 版解决更大规模的异步批处理。 面试时要按演进讲，不要说所有能力一开始就在同一个页面里完成。

09必要但尚未完全做好的方向：面试可作为“下一阶段规划”讲

下面这部分要和“已实现”区分开：它们不是当前已经完整落地的功能，而是把项目从可用升级到更强生产平台的必要方向。

方向 为什么必要 建议做法
密钥与配置治理 本地 service-account / .env 明文不适合生产安全要求。 接入 Secret Manager / Vault / IAM Workload Identity，运行时注入，仓库只保留模板。
统一运行追踪 批量任务失败时，需要快速定位是下载、压缩、定位、抽取还是落表出错。 给每个 run 建 trace：输入清单、prompt 版本、模型版本、文件 hash、token/cost、失败原因、重试记录。
正式 Evaluation Harness LLM 抽取不能只靠人工肉眼验收，需要持续量化。 把 LLM Lab 的验收逻辑沉淀为 CI/批处理评测：按指标类型输出 precision、recall、幻觉率、单位错误、页码错误。
模型路由与成本分层 全部用强多模态模型成本高，简单页/简单指标不一定需要。 用轻模型/OCR/RAG 做候选召回或低风险抽取，复杂图表、扫描页、低置信度样本再走 Gemini Pro/Vertex Batch。
Schema 强校验 模型 JSON 字段可能缺失、类型漂移、单位不规范。 引入 JSON Schema / Pydantic 风格校验，失败自动修复或重试，所有落表前统一规范化。
人工复核闭环 ESG 数据最终要可信，低置信度和争议样本需要人工确认。 把异常样本、人工修正、Prompt 版本和测试集回流，形成 active learning 数据资产。
更完整的文档清理 旧路径、旧输出格式、旧模式说明会影响交接和面试表述。 把 README 分成“原型版 / fast 版 / batch 版”，删除或脱敏旧绝对路径和内部 endpoint。
最新技术路径建议：继续保留多模态 PDF 理解作为复杂报告主链路；同时补一条“低成本文本/OCR/RAG 召回 + 多模态复核”的混合路线，用模型路由把成本和质量平衡起来。

10面试话术：从 30 秒到深挖

30 秒版本

我做的是一个 ESG 报告信息提取系统，输入是企业发布的 PDF 报告和 500 多个指标的需求表， 输出是结构化指标数据，包括指标编码、年份、值、单位、证据页码和原始响应。系统从最早的本地 React 工作台， 演进到支持 Hive SQL 输入、OSS/GCS 文件准备、Vertex Gemini Batch 两阶段处理的生产链路。 核心设计是先做章节定位，再按章节 PDF 做指标抽取，避免全文和所有指标混在一起，提高稳定性和成本可控性。

2 分钟版本

这个项目解决的是 ESG 报告非结构化数据生产问题。报告里很多信息在表格、图片、扫描页和复杂版面里， 传统 OCR/RAG 很容易丢掉版式、表格和图例信息，所以主链路采用 Gemini/Vertex 多模态 PDF 输入。 工程上我没有把整份报告和 500 多个指标一次性塞给模型，而是把指标按 group 和 value_type 组织， 第一阶段用带物理页码标记的 locator PDF 做章节定位，第二阶段切出章节 PDF，再结合对应指标 Prompt 让模型输出 JSON。 结果会经过字段映射、年份拆行、单位处理、原始结果保留和 Hive 双写，后续再用 LLM Lab 做测试集验收和 Prompt 迭代。

如果被问“为什么不用 MinerU + RAG + 文本模型？”

  • 可以用，但不是替代全部链路。 对纯文本章节、简单指标，OCR/RAG 是很好的低成本候选召回；但 ESG 报告里很多关键证据在表格、图片、扫描页、图例和版式关系里。
  • 多模态的必要性来自错误类型。 如果错误集中在表格结构丢失、颜色图例、跨页表格、图片扫描页、页码错位，那么纯文本链路会天然劣势。
  • 最优解是混合路由。 不是所有任务都用最贵模型，而是简单样本走低成本文本/OCR，复杂样本和低置信度结果走多模态复核。

如果被问“项目中最工程化的点是什么？”

可以回答：把 LLM 从一次性调用包装成生产流水线。包括输入规范、文件准备、章节定位、章节切片、结构化 schema、重试限流、Batch 异步、落表、原始响应留存、验收和 Prompt 迭代。
